# r46.2 — text-over-video freeze fix (CMA re-prime memoization)

**Author lane:** code1 (renderer; continuing r46's text-over-
video implementation).

**Scope:** fix the visible-on-FYS freeze where the text-over-
video slide painted correctly ~20% of the time and froze on the
last frame for 3s the other ~80%, looping continuously. Per
QA's r46.2 dispatch + journal probe, the freeze was the
classic `UnsupportedSlide → playback.py 3s held-last-frame
retry` pattern fired by `prime_video_decoder` returning Err
under CMA pressure.

**Origin/main HEAD at fix time:** `b2b225f0` (my r46.1).

**Recommendation (preview):** ship the B.1 memoization fix
(multi-keep `evict_other_video_state`). The bug is mechanically
the same shape r46's `ensure_bg_video_for_text_slide` was
designed for, just on a code path I didn't account for —
single-slide-loop playlists where the same bg video is needed
on every BeginSlide.

---

## §A — Diagnosis (which root cause)

Per dispatch §A options:

1. **A.1 Re-prime leak**: each `ensure_bg_video_for_text_slide`
   primes a new V4L2 pool; the prior pool's release isn't
   completing before the new alloc; CMA accumulates ~24 MB per
   cycle.
2. A.2 held_scanout retention compounding.
3. A.3 Glyph atlas page growth.
4. A.4 Something else.

**Verdict: A.1 is the most plausible AND the fix shape sidesteps
A.1/A.2/A.3 simultaneously** because B.1 (memoize) just avoids
re-priming entirely when the bg video state is already correct.

Evidence:
- QA's journal probe shows cma_used at 254.4 MB persistent (was
  186.9 MB on r46.1 post-restart). 67 MB delta accumulated over
  uptime ≈ 3 × 24 MB pools = ~72 MB. Strong signal for A.1.
- The freeze pattern: `prime_video_decoder` Err →
  `UnsupportedSlide` → 3s hold. This is the V4L2 pool
  allocation failure path. Direct evidence the per-cycle pool
  alloc is failing.
- `force_evict_image_caches_for_cma_pressure` is correctly
  designed but useless here: the freeze playlist has zero
  ImageSlides → image caches are 0/6 + 0/6 → eviction is a
  no-op. r46's mitigation was the wrong shape for the wrong
  case.

The B.1 fix avoids the per-cycle alloc entirely, so whichever
of A.1/A.2/A.3 is the actual leak vector becomes moot.

---

## §B — Mitigation choice + rationale

Per dispatch §B options:

- **B.1 Memoize bg video state across BeginSlide when unchanged**
  → SHIP.
- B.2 Shrink V4L2 pool to 720p size (~12 MB instead of ~24 MB)
  → DEFER. Real but more invasive; touches V4L2 pool config.
  Worth investigating in Phase 9 / r47+. The Open Sign video is
  1280x704 ≈ 720p so this would help — but requires verifying
  bcm2835-codec actually scales pool size with the configured
  dims (it may pad to 1920x1088 internally).
- B.3 Force-evict other CMA consumers (held_scanout, atlas) →
  REJECT. Risky; held_scanout is the canonical anti-black-flash
  contract; evicting it could cause visible flashes.

**B.1 is shipped here.** B.2 is the natural Phase 9 followup if
the freeze recurs on different (larger) videos.

### Why B.1 is clean

The mechanism: `evict_other_video_state(slide_id)` was passed a
SINGLE id and dropped all video state where `key != slide_id`.
For text-over-video, slide_id is the text slide's id, and the
bg video has a DIFFERENT id — so the bg video state was always
evicted. The IPC text-arm then triggered
`ensure_bg_video_for_text_slide` → recursive `cache.load(bg_id)`
→ falls through `video_reprime_needed` → re-primes the V4L2
pool.

The fix: widen `evict_other_video_state` to accept a slice of
keep ids. The BeginSlide handler now computes:

```rust
let bg_video_id = match cache.items.peek(&p.slide_id) {
    Some(ContentItem::Text(s)) => s.background_video_slide_id,
    _ => None,
};
let mut keep_ids = vec![p.slide_id];
if let Some(bg_id) = bg_video_id {
    if bg_id != p.slide_id { keep_ids.push(bg_id); }
}
cache.evict_other_video_state(&keep_ids);
```

On a same-slide loop (text-over-video re-entry): `items[text_id]`
is present (cached from prior BeginSlide), so the lookup
returns `Some(bg_id)`, and `keep_ids = [text_id, bg_id]` — the
bg video state survives. Recursive `cache.load(bg_id)` then
short-circuits (items+mtime hit, demuxer + decoder present
post-evict). No re-prime; no fresh V4L2 alloc; CMA bounded.

Uses `cache.items.peek(&id)` not `cache.items.get(&id)` to
avoid bumping the LRU access order before the evict — get()
would mutate access order which is the wrong semantic for a
lookup-then-evict pattern.

### Edge cases

| Case | keep_ids | Behavior |
| --- | --- | --- |
| First BeginSlide ever for a text-over-video slide | `[text_id]` (items[text_id]=None → bg_video_id=None) | bg video gets primed on cache.load's recursive path; subsequent re-entries memoize |
| Text-over-video slide, same id, looping | `[text_id, bg_id]` | bg video state preserved; no re-prime |
| Text-over-video slide → different text slide (different text_id, same bg_id) | New cycle: keep_ids=[new_text_id, bg_id] for the new slide | bg video state preserved (same bg_id) |
| Text-over-video slide → different text slide (same text_id structurally but different bg_id) | New cycle: keep_ids=[text_id, new_bg_id] | OLD bg video dropped; new bg video primed via cache.load. Correct. |
| Text-over-video → standalone Video → text-over-video same bg | First cycle: keep_ids=[text_id, bg_id]; second: keep_ids=[video_id]; third: keep_ids=[text_id, bg_id] | Standalone video drops bg state; third re-primes. Acceptable cost — three-way alternation between distinct video states is a real eviction event. |
| Plain text slide (no bg video) | `[text_id]` (bg_video_id=None) | Standard single-keep behavior |
| Image slide | `[image_id]` (peek matches `Some(ContentItem::Image)` arm in match → None bg_video_id) | Standard single-keep behavior |
| Standalone Video slide | `[video_id]` (peek matches Video arm → None) | Standard single-keep behavior |
| Same id text-over-video where bg_id == text_id (text slide bg-refs itself) | `[text_id]` (the `bg_id != p.slide_id` guard) | bg_id NOT added to keep_ids; standard single-keep. The infinite-recursion case is defended in `ensure_bg_video_for_text_slide` too. |

## §C — CMA budget math

**Pre-r46.2 (observed):**
- cma_used baseline post-r46.1 restart: 186.9 MB
- Per re-prime cycle: +~24 MB (V4L2 pool) accumulated
- After ~3 cycles: 186.9 + 72 = ~259 MB ≈ above 254 MB watchdog
  threshold + above 256 MB CMA pool ceiling
- Result: V4L2 alloc fails → UnsupportedSlide → freeze

**Post-r46.2 expected:**
- Same-slide loop: V4L2 pool allocated ONCE (first BeginSlide)
- All subsequent BeginSlides: bg video state memoized, no
  re-prime
- cma_used stable at ~186.9 + 24 = ~211 MB (initial baseline +
  one V4L2 pool)
- Well below the 254 MB watchdog threshold + the 256 MB CMA
  pool

**Multi-slide playlist with different bg videos:**
- Each slide change: drop prior bg, prime new bg (one ~24 MB
  cycle per actual slide change)
- This is the design intent — pool alloc per ACTUAL slide change
  is correct + bounded (one pool live at a time)
- CMA might briefly spike to 234 MB (baseline + prior pool not
  yet released + new pool) but converges to baseline + one pool
  steady-state

## §F — Sweep findings (§F.new)

Sacred subagent review pre-commit returned **SHIP** with 2 nits
(both flagged here for record):

1. **One-cycle mtime-drift orphan** (nit). If the operator edits
   a text slide on disk to change `background_video_slide_id`
   from OLD_BG to NEW_BG, the `peek` returns the pre-invalidation
   cached entry (OLD_BG) → keep_ids = [text_id, OLD_BG]. Then
   `cache.load(text_id)` mtime-drift-detects + invalidates +
   re-loads with NEW_BG → primes NEW_BG. OLD_BG's V4L2 state is
   orphaned in `video_demuxers`/`video_decoders` until the NEXT
   BeginSlide evicts it. **Self-healing on the next BeginSlide**;
   transient one-cycle leak (≤24 MB). Not blocker-grade; the
   orphan is the COMMON case for slide-edits + the next eviction
   is at most one slide-change away.

2. **3-way alternation re-prime cost** (nit). Audit §B edge-
   case table notes the playlist `[text-over-video-A, standalone-
   video-V, text-over-video-A]` re-primes bg-B every cycle of A
   (the V slide drops B; next A cycle re-primes B). r46.2's
   memoization only helps when the SAME slide_id loops; multi-
   slide playlists where bg-B appears between OTHER video slides
   still pay the re-prime cost. Acceptable per dispatch's
   "memoize ... when slide_id unchanged" framing. **Worth
   flagging as Phase 9 followup** alongside B.2 V4L2 pool size
   tuning if such playlists become common.

Both nits documented in this audit doc only; no code change.

## Verified-clean properties (subagent confirmed)

- Memoization correctness: `peek` is immutable `&self`; no LRU
  mutation; `bg_id != p.slide_id` defensive guard correct;
  single-threaded handler so race-free.
- No regression: standalone-video, image, plain-text, alternating-
  text-with-shared-bg all walk through cleanly. Edge-case table
  matches code.
- Compile: `Option<&ContentItem>` lookup → `Option<Uuid>` extract
  (Uuid is Copy, lifetime ends at match scope); subsequent `&mut`
  evict NLL-safe. `<[Uuid]>::contains(&Uuid)` works via
  PartialEq.
- CMA math: 186.9 + 3×24 = 258.9 ≈ 254.4 observed ceiling;
  post-fix 186.9 + 24 = 210.9 ≈ 211 stable target. Math
  consistent.
- Fix changes curve: same-slide loop has ZERO fresh V4L2 alloc
  on cycles N+1, N+2, ... — both cache.load(text_id) AND
  recursive cache.load(bg_id) short-circuit via items+mtime hit.
- Sweep: no other `evict_other_video_state` callers or
  `video_demuxers.retain` / `video_decoders.retain` outside
  ipc_main.rs. All 3 production+test callers updated.
- Pacing: B.1 vs B.2 defense sound — B.2 only halves the per-
  pool cost; the LEAK still accumulates. B.1 fixes the root
  cause.
