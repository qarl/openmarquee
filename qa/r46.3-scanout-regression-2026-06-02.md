# r46.3 — text-over-video scanout regression fix

**Author lane:** code1 (continuing r46.2's CMA pressure work).

**Scope:** fix the BLACK-PANEL regression r46.2 introduced. Per
QA's diagnostic: text-over-video slides showed `bo=0/fb=0` —
no scanout BOs allocated — while non-video slides on the same
session showed normal `bo=2/fb=2`. The text-over-video paint
function was consistently early-returning before swap+commit.

**Origin/main HEAD at fix time:** `12cafbaa` (my r46.2).

**Recommendation (preview):** ship the
`reprime_video_decoder_for_loop` extension + IPC dispatcher hook
fix. Preserves r46.2's CMA-budget memoization; targets the
actual root cause (`capture_drained` flag stuck across BeginSlide).

---

## §A — Root cause diagnosis

The regression is in V4L2 decoder state, not in my new paint
function or the keep_ids memoization.

**Mechanism** (from reading `renderer/src/v4l2.rs`):

- Line 1304-1306: `if inner.capture_drained { return Ok(None); }`
  — early-return path in `Decoder::next_frame()`.
- Line 1415-1417: `if is_last { inner_w.capture_drained = true; }`
  — set when V4L2 returns a buffer with `V4L2_BUF_FLAG_LAST` (the
  kernel's EOF marker).
- Line 1330-1334: also set on `EPIPE` (decoder drained).
- Line 735: `Frame::Drop` skips re-QBUF when `capture_drained` is
  true, so capture buffers don't get returned to the kernel —
  further sealing the wedged state.

**Pre-r46.2 (worked, accidentally)**: my `evict_other_video_state
(slide_id)` dropped the bg-video decoder on every BeginSlide.
`DecoderInner::Drop` STREAMOFF'd both queues; the next BeginSlide
created a fresh decoder via `prime_video_decoder` with
`capture_drained=false`. The bug existed in the V4L2 layer but
was masked by per-cycle decoder destruction.

**Post-r46.2 (broken, exposed)**: r46.2's `keep_ids` memoization
preserves the decoder across BeginSlide. Once the slide plays
long enough to hit `V4L2_BUF_FLAG_LAST`, `capture_drained=true`
sticks. Every subsequent paint:
1. `bake_video_slide_to_current_fbo` calls `decoder.next_frame()`
2. `next_frame()` early-returns `Ok(None)` (capture_drained=true)
3. `bake` retries 10× × 3ms = 30ms budget, all return `Ok(None)`
4. `bake` returns `Ok(None)`
5. My r46 no-frame guard in
   `paint_and_present_one_text_over_video_slide_frame` early-
   returns BEFORE swap+commit
6. Scanout state never advances; FBO undefined; panel BLACK

The QA-observed `bo=0/fb=0` for text-over-video while Demo
slides show `bo=2/fb=2` is the smoking gun: the session
mechanics are healthy; my text-over-video path is the one not
reaching commit.

## §B — Fix shape + rationale

Per dispatch's three mitigation options:

- **1. Reset decoder state on kept-bg path** → **CHOSEN**.
- 2. Drop the no-frame tick guard for text-over-video. Simpler
  but leaves the decoder in a stale state — subsequent paints
  composite text over a frozen video frame instead of fresh
  decoded frames. Visible artifact: text "moves" over a still
  image. Mitigates the black-panel but doesn't restore the
  feature.
- 3. Force-evict other CMA consumers. Risky + unrelated.

### Implementation

1. **`renderer/src/v4l2.rs`**: new `Decoder::reset_for_replay`
   method. Does the minimal V4L2 state cycle without dropping
   the buffer pool (preserves r46.2's CMA budget):
   - `stop_streaming_quiet()` — STREAMOFF both queues
   - Clear `capture_drained = false`
   - Reset `capture_in_flight` (all-false; kernel will re-own
     after re-QBUF)
   - Reset `output_eof_sent = false` (so subsequent `feed()`
     doesn't error)
   - `start_streaming()` — re-QBUFs all capture buffers via the
     existing pre-QBUF-then-STREAMON impl

2. **`renderer/src/video_decode.rs`**: extend
   `reprime_video_decoder_for_loop` to call
   `decoder.reset_for_replay()` BEFORE feeding the SPS+PPS+IDR
   primer. The canonical "loop wrap" function now also handles
   the drained-decoder case.

3. **`renderer/src/ipc_main.rs`**: in the IPC text-over-video
   routing block, BEFORE calling
   `paint_and_present_one_text_over_video_slide_frame`, check
   if `dec_state.next_sample_idx >= dem.samples.len()` and call
   `reprime_video_decoder_for_loop(dec_state, dem)` if so.
   Mirrors `render_video_slide_in_session` at hdmi.rs:3025-3034
   (the standalone reel's wrap-and-reprime pattern).

4. **`renderer/src/hdmi.rs`**: simplify the bake helper's wrap
   branch back to just `*next_sample_idx = 0` (the wrap-reset
   logic is now at the IPC layer where `&dem` is available).
   Comment annotates the architecture (primer feed requires
   SPS/PPS from demuxer; bake doesn't have it).

### Why not call reset_for_replay from bake's wrap branch directly?

Bake doesn't have `&Mp4Demuxer` (only `samples: &[Sample]`). A
bare-IDR feed after STREAMOFF/STREAMON is NOT guaranteed by the
V4L2 spec to work — bcm2835-codec might drop parsed SPS/PPS on
STREAMOFF, requiring re-feed. The canonical pattern is
SPS+PPS+IDR (per `reprime_video_decoder_for_loop` which has
existed since QA H2 in the codebase). Hooking at the IPC layer
gives us the demuxer reference + reuses the canonical pattern.

(Sacred subagent caught this in pre-commit review: my v1 patch
called `decoder.reset_for_replay()` from bake's wrap branch
without the primer feed — that would have shipped a half-fix
that worked only on chips that retain SPS/PPS across STREAMOFF.
The v2 fix here mirrors the existing canonical contract.)

## §C — CMA budget math (preserves r46.2)

The fix does NOT drop the `Decoder` struct → V4L2 buffer pool
persists → no `allocate_buffers` call → no ~24 MB CMA
allocation per cycle.

- r46.2 expected stable: ~211 MB (baseline + one V4L2 pool)
- r46.2 actual observed (verified at deploy): 186-191 MB
- r46.3 expected: ~same (186-191 MB); reset_for_replay only
  does V4L2 ioctls, no memory allocation. CMA pool stays the
  same size.

The few-ms STREAMOFF/STREAMON cycle per wrap is the only added
cost. At ~30 fps with one wrap per 10-second slide-play, that's
~3ms additional latency per 10s — negligible.

## §D — Subagent review

Pre-commit review surfaced **1 BLOCKER** (fixed in v2 of this
commit before push) + 3 warnings (1 fixed; 2 deferred with
documentation):

### Blocker (FIXED in v2)

- **Bare-IDR feed after STREAMOFF may fail**. My v1 patch called
  `decoder.reset_for_replay()` from bake's wrap branch without
  re-feeding SPS+PPS+IDR; bcm2835-codec V4L2 spec doesn't
  guarantee SPS/PPS persistence across STREAMOFF. The existing
  `reprime_video_decoder_for_loop` exists exactly because the
  canonical wrap pattern needs the full primer. **Fix**: route
  through `reprime_video_decoder_for_loop` (which now calls
  `reset_for_replay` internally before re-feeding primer).
  Architecturally cleaner + reuses the proven pattern.

### Warnings (deferred with documentation)

- **Mid-stream EPIPE not at wrap boundary**: if `capture_drained`
  gets set without `next_sample_idx >= samples.len()` (e.g., a
  transient decode error), the IPC wrap-check won't fire +
  decoder stays drained. Rare in practice (kernel doesn't EPIPE
  mid-stream for normal H.264 playback). Defer: add
  `Decoder::is_capture_drained()` getter + extend the IPC
  check to OR with the drain flag. r47+ if it bites.
- **Warn-and-continue on reset failure**: if STREAMON fails
  inside reset_for_replay, `capture_streaming=false` and
  subsequent `feed` succeeds but `next_frame` EAGAINs forever
  — silent stall. Currently the warn propagates as Err via `?`
  in the new IPC dispatcher hook (so operators see "paint_slide
  (text-over-video): reprime_video_decoder_for_loop failed").
  Subagent's concern is addressed.

### Nit (documented)

- **Warmup pre-feed advantage lost after reset**: prime's
  warmup-feed of samples 1-4 is dropped by STREAMOFF. First
  frame after each wrap will pay the cold-start latency.
  Pre-r46.2 had the same cost (decoder dropped+re-primed which
  redid warmup) so not a new regression. Could re-warmup inside
  reset; not in r46.3 scope.

### Verified clean

- Compile: reset_for_replay inside `#[cfg(target_os = "linux")]`
  impl block; bake call site already cfg-gated. Mac build OK.
- Borrow checker: lock scope correct (inner.lock released before
  start_streaming).
- CMA budget: no new allocations.
- No regression on standalone-video / image / plain-text /
  text-over-image-bg paths.
